## Open

- [ ] `WS /repos/{id}/progress` clients can hang forever if the final "ready" Redis publish fails, even though the underlying data is correct (found while working on: Phase 1.5 `worker/pipeline.py`, 2026-08-11, found by the local Codex pre-push review; deliberately deferred, not fixed).
      By the time `index_repo` publishes the terminal "ready" message, `complete_snapshot` has already committed — a Redis failure on just that publish call leaves a connected websocket (one that already passed its initial DB-status check and is sitting in `pubsub.listen()`) waiting for a message that will never arrive, even though the snapshot is genuinely done. A real fix needs either publish-retry logic or a polling fallback on the WS side — both are new design surface, not a quick patch, for a failure window this narrow (Redis has to fail on that one specific call, nothing else) with a bounded, self-healing consequence (reconnect/refresh sees "ready" immediately via the WS handler's own DB-read-first logic). Revisit if this ever actually happens in practice, or before this pipeline handles higher-stakes/longer-running jobs where a stuck client is more costly.
- [ ] `main` has no branch protection (found while working on: CI pipeline setup, 2026-08-11)
      GitHub's branch protection and rulesets APIs both refuse private repos on the free tier (`403: Upgrade to GitHub Pro or make this repository public`) — confirmed by trying both. The PR-before-merge habit is documented in `CLAUDE.md` but not technically enforced; nothing stops a direct push to `main`. Revisit if the repo goes public or gets a Pro upgrade.
- [ ] Frontend has no test runner configured (found while working on: CI pipeline setup, 2026-08-11)
      `frontend/package.json` only has `lint` (oxlint) and `build` (tsc + vite) scripts — no `test` script, so `.github/workflows/ci.yml`'s `frontend-build` job only lints and builds. Add `vitest` (fits the existing Vite setup) once frontend logic exists that's worth unit-testing.
- [ ] `entry_points.py` heuristics regex-match raw file bytes, not parsed AST (found while working on: Phase 1 `analysis/entry_points.py`, 2026-08-10)
      Means a file that merely *mentions* `FastAPI(`, `WorkerSettings`, etc. in a comment/string/docstring gets flagged as an entry point, not just files that actually call/define them — confirmed by dogfooding: `entry_points.py` flags itself, since its own reason strings contain the literal pattern text. Low priority — real target repos (Flask/FastAPI apps) are very unlikely to hit this; would need AST-aware call-expression detection (reusing parser.py's tree-sitter trees) to fix properly.

## Resolved

- [x] Eleven gaps in the Phase 1.5 job-queue refactor, caught across six rounds of the local Codex pre-push review before the PR was even opened (found + resolved while working on: Phase 1.5 `worker/pipeline.py` + `api/repos.py`, 2026-08-11):
      (1) Any exception besides `SourcePreparationError` during indexing left the snapshot stuck at `parsing` forever with every WS client hanging indefinitely — `index_repo` now catches `Exception` broadly, marks `failed`, publishes, and re-raises so arq still logs it. (2) A Redis failure between committing the pending `Repo`/`AnalysisSnapshot` and enqueueing the job stranded them at `pending` with no job ever created, while the client saw a bare 500 — `create_repo` now marks the snapshot failed and returns a `503` if enqueueing itself fails. (3) `await file.read()` buffered the entire zip upload into memory before any size check ran — now reads `zip_upload_max_bytes + 1` bytes and rejects anything longer, bounding worst-case memory regardless of upload size. (4) `git ls-remote` ran synchronously inside the async request handler, blocking the whole event loop (including other clients' progress websockets) for its duration — now runs via `asyncio.to_thread`. (5) That fix's own first version only bounded the *coroutine* awaiting the thread (`asyncio.wait_for`), not the underlying `git` subprocess — a slow/hung remote left the thread and process running indefinitely regardless. Confirmed via a real hanging-socket test, then fixed with GitPython's `kill_after_timeout`, which actually SIGKILLs the process. (6) `get_redis_pool`'s `create_pool()` call itself can fail (confirmed empirically — it eagerly `ping()`s) before `create_repo`'s body, and thus its own try/except, ever runs — surfaced as a bare 500. Added an app-level `RedisError` exception handler in `main.py` for this specific case (dependency-resolution-time failure, nothing committed yet — distinct from #2, which handles failure *after* commit). (7) The worker itself ran `clone_git_repo`/`extract_zip_upload`/`analyze_source` directly on its own event loop — since arq runs concurrent jobs on one loop, a single slow clone or big-repo parse blocked every other queued job and all progress publishing, reintroducing the exact blocking problem the whole refactor was meant to remove, just one level down. Now wrapped in `asyncio.to_thread`. (8) `complete_snapshot` wasn't idempotent under job redelivery (arq is at-least-once, not exactly-once) — a second run for the same snapshot re-inserted every `CodeUnit` on top of the first, duplicating them. Confirmed by deliberately breaking the fix and re-running the test (4 units instead of 2). Fixed by deleting existing units for that snapshot before inserting. (9)+(10) The zip-upload Redis key was explicitly deleted on both the success path and the bad-source-failure path — first round found `except Exception` doesn't catch `asyncio.CancelledError` (job timeout/worker shutdown, a `BaseException`), so that path hit a shared `finally` that deleted the source data right before arq's own `retry_jobs` logic redelivers on `CancelledError`; second round found even the *success* path's explicit delete raced a worker crash between the DB commit and arq recording the success, which could turn an already-`ready` snapshot back to `failed` on redelivery. Both traced through arq's actual source to confirm reachability, not assumed. Resolved by removing explicit deletion entirely — the TTL already set on the key when it's written (`api/repos.py`) is now the sole cleanup mechanism, on every path, which is both simpler and correct under redelivery. (11) The initial `parsing` status-update + publish ran *before* the try block — if that specific publish failed, the snapshot was already committed `parsing` but nothing ever caught the failure to mark it `failed`, leaving it permanently stuck with the same "client waits forever" consequence as gap #1. Moved inside the guarded try. A sibling gap in the *final* "ready" publish (same failure mode, opposite end of the pipeline) was deliberately left open rather than fixed here — see the Open section, since a real fix needs new design surface (publish-retry or WS-side polling), not a quick patch. All eleven guarded by new tests in `tests/worker/test_pipeline.py`, `tests/api/test_repos.py`, and `tests/analysis/test_snapshot.py`.
      Known residual gap, not chased further: GitPython's `kill_after_timeout` (used for the ls-remote pre-check, #5) does not reliably bound `Repo.clone_from` itself — confirmed empirically, a hung remote still ran the full duration regardless of the timeout passed. The worker-side clone is at least now off the event loop (#7), so a hang there only ties up one background thread rather than blocking the whole worker; a fully bulletproof subprocess-level kill for the clone itself would need a different mechanism than GitPython offers. Low priority for a solo local repo with no adversarial traffic.
- [x] CI's `backend-test` job had no Redis service container (found while working on: CI pipeline setup, 2026-08-11).
      Resolved at the start of Phase 1.5 by adding a `redis:7` service container + healthcheck to `.github/workflows/ci.yml`, mirroring the existing Postgres setup.
- [x] `validate_zip_upload`'s zip-slip check false-positived on every valid entry when called without an extraction-target path (found while working on: Phase 1.5 `api/repos.py`'s synchronous pre-check, 2026-08-11).
      `tempfile.gettempdir()`'s fallback wasn't `.resolve()`d, but the zip member paths it was compared against were — on macOS, `/tmp` is a symlink to `/private/tmp`, so the comparison never matched and rejected every upload as "escaping" the directory. Resolved by unconditionally `.resolve()`ing the fallback in `ingestion/source.py`. Caught by the test suite (`test_create_repo_from_zip_upload`), not by inspection.
- [x] `app/redis_pool.py`'s Redis connection was a module-level singleton, unlike the DB engine's `NullPool` (found while working on: Phase 1.5, 2026-08-11).
      Broke with `RuntimeError: Event loop is closed` the moment two different `TestClient` blocks (each spins up its own event loop) used it, since the cached connection stayed bound to whichever loop created it. Resolved by making it a per-request connection (FastAPI generator dependency, closed after each request/WS connection) instead of a cached singleton — same reasoning `db/session.py`'s `NullPool` comment already documented, just not applied consistently to the new Redis dependency.
- [x] `complete_snapshot` raised an unhandled `ValueError` if its target `AnalysisSnapshot` row no longer existed, unlike `set_snapshot_status`'s existing tolerance for the same condition (found via a real end-to-end smoke test, not pytest, 2026-08-11: a manual worker run drained a real job enqueued by an earlier `POST /repos` test, by which point `clean_db` had already wiped the row).
      A vanished target is a legitimate runtime condition (repo deleted mid-index), not just a test artifact. Resolved by making `complete_snapshot` return `None` instead of raising, matching `set_snapshot_status`; `worker/pipeline.py` skips the final "ready" publish in that case. Guarded by `tests/worker/test_pipeline.py::test_index_repo_tolerates_snapshot_deleted_mid_job`.
- [x] `claude-review.yml` asked Claude to call `gh pr comment`/inline-comment tools itself — worked on a small docs-only PR, failed on Phase 1.5's real multi-file diff: first attempt (posting-tools-only `--allowedTools`) hit 43 permission denials and posted nothing; widening to add `Read`/`Grep`/`Glob` (found on PR #5, 2026-08-11) dropped that to 15 denials but still posted nothing, and GitHub Actions redacts the action's detailed tool-call log by default (`show_full_output: false`), so the exact remaining denials weren't cheaply diagnosable.
      Root-caused as an architecture problem, not a permissions-tuning problem: an LLM reliably chaining multiple GitHub API tool calls under a CI job's time/turn budget is inherently flaky. Resolved by having Claude return structured findings via `--json-schema` instead (confirmed locally: zero GitHub tool access needed, `permission_denials: []`) and posting them in a separate, deterministic `actions/github-script` step — the same architecture the Codex Action option already used. Per the workflow-file self-verification gotcha (`CLAUDE.md`), this fix can't be confirmed from its own PR — verify on whichever PR merges next. (The PR making this exact change hit that gotcha immediately: the action's own skip left `structured_output` empty, and the downstream write/upload/post steps weren't guarded for that, so the job failed trying to parse nothing rather than just skipping quietly — fixed by adding `if: steps.claude.outputs.structured_output != ''` to each of them.)
- [x] tree-sitter core (0.26.0) + latest tree-sitter-python/-javascript (0.25.0, ABI 15) alongside tree-sitter-typescript's latest release (0.23.2, ABI 14) caused reproducible native segfaults during parsing (found while working on: Phase 1 `analysis/snapshot.py` orchestration checkpoint, 2026-08-10).

Revisit only once tree-sitter-typescript ships an ABI-15 build. Now guarded by `tests/test_tree_sitter_smoke.py`.
- [x] `db/session.py`'s module-level async engine used the default connection pool, which broke ("Future attached to a different loop") whenever DB access happened from a different event loop than whichever one first touched the engine — reproducible with pytest-asyncio fixtures + `TestClient` in the same test (found while working on: Phase 1 API test suite, 2026-08-10).
      Resolved by switching the engine to `NullPool` (no cross-loop connection reuse). Also would have eventually bitten Phase 1.5's worker process. Now guarded by `tests/api/test_repos.py`.
